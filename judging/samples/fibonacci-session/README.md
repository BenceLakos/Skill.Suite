# Fibonacci — a worked white-box session

A complete, runnable session module, small enough to read in one sitting. It exists to answer two questions
that documentation alone cannot: *what does a session author actually have to write?* and *does the whole
chain — push, webhook, clone, judge, parse, results — really work?*

Everything a real S1/S3 session has is here and nothing else: a contracts package, a reference
implementation, a hidden graded suite, the answer-key firewall, and a marking map.

```
Fibonacci.Contracts/       IFibonacci — packed to local-nuget/, handed to the competitor
Fibonacci.Services/        the reference implementation; NEVER enters the image (see .dockerignore)
Fibonacci.UnitTests/       the hidden graded suite, one [Aspect] per test case
competitor-start/          what a competitor is given — GENERATED by make-competitor-start.sh
submissions/complete/      a submission that scores every aspect
submissions/partial/       a submission with three broken edge cases — the interesting demo
marking-map.json           aspect ids and labels, for `skill-marker report`
```

## Build the judge image

```bash
cd judging/samples/fibonacci-session && ./pack-contracts.sh
```

```bash
cd judging/samples/fibonacci-session && BASE_IMAGE=skill-suite-judge-base:9.0 ./build-image.sh
```

`pack-contracts.sh` must run first: the image restores offline from `local-nuget/`, and the build fails
`NU1101` without it. Drop `BASE_IMAGE` once `judge-base` is published — the default points at the registry.
There are no session build arguments: `Dockerfile` declares the solution, the swapped folder and the test
project as `ENV`, because those are facts about this module.

The build fails on purpose if `Fibonacci.Services/*.cs` reaches the image. That check is not decoration: a
competitor can `docker pull` any image they are told to run.

## Regenerate the starter kit

```bash
cd judging/samples/fibonacci-session && ./make-competitor-start.sh
```

`competitor-start/` is derived from `Fibonacci.Services`, not maintained by hand, and the script compiles the
result to prove it still builds against `IFibonacci`. This folder is also what the running platform uses as a
session's **template folder**, so regenerate it after changing the contract or the reference implementation.

## Run one submission, no platform needed

```bash
judging/tools/judge-run.sh fibonacci-judge:1 judging/samples/fibonacci-session/submissions/partial
```

This mirrors `ProcessContainerRunner` exactly — read-only mount, `-w /workspace`, two env vars — and prints
the exit code and the resulting events. Expect 17 of 20 tests to pass and exit code 0: in a white-box session
red tests are a *result*, not a failed run.

## Run the whole platform

```bash
E2E_PERSONA=judging/samples/fibonacci-session/submissions/partial judging/verification/e2e/run-e2e.sh fibonacci-judge:1 fibonacci-alice
```

Brings up Postgres, Gitea and the application, provisions a session and competitor, pushes the submission,
and waits for the results to land. See [`../../verification/e2e/README.md`](../../verification/e2e/README.md),
or `MANUAL.md` beside it to do the same thing by hand.

## How grading works here

One test case is exactly one aspect, and an aspect counts as satisfied only when **every** test claiming it
passes. `A3.2` in the partial submission is the case worth looking at: two of its three theory rows pass and
one fails, so the aspect is not satisfied — a competitor cannot bank most of an aspect.

`[Aspect(..., CompetitorVisible = true)]` is the leak dial. Eight of the eleven aspects here are visible, so
the bar a competitor sees moves when they fix something; the three hidden ones (`A1.4`, `A2.3`, `A4.2`) still
grade but reveal nothing. The competitor sees a coarse bucket, never a number, and never which aspect failed.

| submission | tests | visible aspects satisfied | bucket |
|---|---|---|---|
| `complete` | 20/20 | 8 / 8 | VeryHigh |
| `partial`  | 16/20 | 5 / 8 | High |

## Writing the suite

Two rules, both enforced by the harness rather than by review:

- Derive from `LoggedTest<TSelf>` and take `IClassFixture<FixtureScope<TSelf>>`. Without the fixture there is
  no `start-fixture`/`finish-fixture` pair and the platform records nothing.
- Assert through `Log`, never bare `Assert`. A bare assertion still fails the test but emits no event, so the
  result arrives as a red row with nothing explaining it.

Resolve the service with `ServiceResolver.Resolve<T>().WithCallLogging()`. The proxy records every call with
its arguments and return value, which is what makes a disputed result reviewable after the fact, and it
enforces the nullability contract declared on the interface.
